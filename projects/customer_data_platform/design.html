System design

One customer record, and the receipts for it

CRM, Billing and Support each think they own the customer. They disagree about her name, they send updates out of order, and every one of them sends a partial record. This is a design for the service that turns those three streams into one profile that can justify every field it holds.

Java 21 · Spring Boot 4.1 · Kafka · PostgreSQL 16 · Redis · S3

The disagreement, concretely

Three systems, one human, seven minutes of real time between the updates. Nothing here is malformed — this is what a healthy day looks like.

Billingb-30117Alexandra M Riveraa.rivera@example.com—2025-03-06 09:12
Supportz-99421alex riveraalex.rivera@exampl.com(415) 555 01482025-02-28 16:40

Three different questions hide in that table, and conflating them is the usual mistake:

  • The two phone numbers are not a conflict — they are one number in two formats. That is a normalization problem, and it must be solved before anything compares values.
  • The three names are a conflict, and recency is the wrong tiebreak. Billing's version is the one on the payment instrument; that is why Billing wins names, not because it happened to update last.
  • Support's email is a typo. Nothing in the data says so. The system's job is not to be right about it — it is to not let a low-authority source overwrite a high-authority one, and to show a human exactly what it rejected and why.

The design decision everything else follows from: the unified profile is not a row that sources take turns updating. It is a pure function over an append-only set of field observations, recomputed on every arrival.

Records are never merged into each other. Each incoming record is exploded into one immutable observation per field, and the winning value for a field is derived from every observation ever seen for it. Two properties fall out for free, and they are exactly the two hard requirements: out-of-order delivery stops mattering, because a late event just adds a candidate and the function returns the same answer either way; and lineage stops being a feature you build, because the explanation is the candidate set plus the rule that fired.

Architecture

Three Spring Boot services, one bus, one database that holds evidence rather than state.

How one record moves

The flow every incoming record follows, including the three ways it can leave early.

  1. Ingest

    One endpoint per shape, not per source: POST /v1/records takes a source envelope plus an opaque payload. Each source authenticates with its own credential, and the envelope must carry eventId, sourceRecordId and sourceUpdatedAt. The response is 202 Accepted — a source waiting on identity resolution would couple its write latency to our merge logic.

  2. Archive before interpreting

    The accepted envelope goes to records.raw and to S3 byte-for-byte. Every later stage is a derived view of this. If normalization loses a field or survivorship picks wrong, the fix is a new rule plus a replay, not a data-repair script.

  3. Normalize to the canonical schema

    Source-specific mappers produce one canonical record: phones to E.164, emails trimmed and lowercased, names case-folded for comparison but stored as sent, addresses through a single verification provider. The active normalizerVersion is stamped on every observation — a normalization change is retroactive, and you need to know which rows predate it.

  4. Explode into observations

    The canonical record is split into one row per populated field. A field the source omitted produces no row, which is how incomplete records stop being destructive: absence is silence, not a null that overwrites. Clearing a value requires an explicit tombstone.

  5. Resolve identity

    Match keys are looked up in identity_key. Unmatched, we allocate a customer_id. Matched, we attach. If the record's keys point at two existing customers, that is a merge, and merges are the one order-sensitive thing here — see below.

  6. Re-resolve and log the decision

    Only the fields the record touched are recomputed, over their full candidate set. Every change writes a decision_log row holding the rule that fired and the candidates it beat. Unchanged fields write nothing.

  7. Emit

    An outbox row is written in the same transaction as the profile change, and a relay publishes profile.changed carrying only the changed fields with their before and after. A consumer that only cares about email is not woken by a phone-number correction.

Out-of-order delivery

Sources retry. Backfills replay yesterday. A webhook and a nightly file describe the same change and land hours apart. Any design where the profile row is overwritten by whichever message arrives last is a design that is silently, intermittently wrong — and wrong in the worst way, because the data looks plausible.

Choosing a value, and being able to say why

Survivorship is four rules applied in order. They never consult the current profile.

  1. Only authoritative sources are candidates. A source not listed for a field is dropped before anything else happens. Billing sending a lifecycleStage is not a low-priority opinion, it is noise, and letting it compete would mean a field could be decided by a system that has no way of knowing the answer.
  2. Authority tier beats recency, and never the other way round. Support may not overwrite a billing address just because the agent typed one more recently than the payment processor sent one. Recency only ever competes inside a tier.
  3. Within the winning tier, the greatest sourceUpdatedAt wins — and if that winner is a tombstone, the field is cleared. The source's clock, not ours. Ingest time is recorded but is never a tiebreak; it encodes arrival order, which is precisely what we removed.
  4. Ties break deterministically on eventId. Not on a generated row id, and never at random. A replay from S3 mints new row ids, so a row-id tiebreak would let a replay settle on a different answer than the original run — and convergence is the whole point.

Authority is per field because sources are authoritative about different things — this table is the actual policy, and it is configuration, not code:

The explanation is a query, not a log line. Because the winner is a function of stored candidates, "why is her email this?" is answered by re-running the rules over the current candidate set and reporting which one each rule eliminated. decision_log records what changed and when; the lineage endpoint reconstructs the reasoning. Those are different questions and they need different structures.

Identity resolution

Matching is deterministic on normalized keys. Keys are split into two classes, and the split is the entire safety mechanism.

ClassKeysWhat it may do alone
Strongemail, phone, accountNumber, taxIdAttach a record to a customer, and link two customers
Weakname + postalCode, deviceId, householdAddressNothing. Two weak keys agreeing may attach, never merge

A weak key alone merging customers is how a family that shares a household address becomes one person, and how a shared support login collapses an entire small business into its office manager. Un-doing that is expensive and visible — every downstream consumer has already acted on the wrong profile — so the guardrails are deliberately conservative:

  • A merge requires two independent strong keys in agreement, or a human in the review queue.
  • A merge that would make a customer's identity component exceed 25 keys is refused and queued. Real people do not accumulate that many identifiers; that shape is a shared inbox.
  • Merges are reversible. The losing customer_id is never deleted — it moves to customer_alias, so downstream systems holding it keep resolving forever, and an unmerge is a delete of one alias row plus a re-resolve, not archaeology.
  • Merges are the one order-sensitive operation here, so they are serialized per identity component with a row lock on customer and taken in customer_id order to avoid deadlock between two concurrent merges.

Data model

Evidence in one table, the derived answer in another, the reasoning in a third.

schema.sql — the core of it 
create table customer (
    id         uuid primary key,
    created_at timestamptz not null default now(),
    status     text        not null default 'ACTIVE'
);

-- A customer_id retired by a merge. Never deleted: downstream systems are
-- holding it, and they must keep resolving forever.
create table customer_alias (
    alias_id    uuid primary key references customer(id),
    customer_id uuid not null references customer(id),
    merge_id    bigint not null,
    merged_at   timestamptz not null default now()
);

create table identity_key (
    key_type    text  not null,          -- EMAIL | PHONE | ACCOUNT_NUMBER | NAME_POSTCODE | …
    key_hash    bytea not null,          -- sha256(key_type || normalized || pepper)
    customer_id uuid  not null references customer(id),
    strength    text  not null,          -- STRONG | WEAK
    first_seen  timestamptz not null default now(),
    primary key (key_type, key_hash)
);
create index on identity_key (customer_id);

-- The only mutable link in the system. A merge rewrites rows here and nowhere else.
create table record_owner (
    source           text not null,
    source_record_id text not null,
    customer_id      uuid not null references customer(id),
    primary key (source, source_record_id)
);
create index on record_owner (customer_id);

-- Append-only. Never updated. Never deleted outside an erasure request.
create table observation (
    id                 text        not null,     -- ULID, time-ordered
    source             text        not null,
    source_record_id   text        not null,
    field              text        not null,
    value              jsonb,                    -- null iff tombstone
    tombstone          boolean     not null default false,
    source_updated_at  timestamptz not null,
    event_id           text        not null,
    normalizer_version int         not null,
    ingested_at        timestamptz not null default now(),
    -- Postgres requires the partition key in every unique constraint, hence the
    -- leading source_record_id. It costs nothing: an event_id belongs to exactly
    -- one source record, so the uniqueness is the same either way.
    primary key (source_record_id, id),
    unique (source_record_id, event_id, field)
) partition by hash (source_record_id);
create index on observation (source, source_record_id, field);

create table profile_field (
    customer_id            uuid not null references customer(id),
    field                  text not null,
    value                  jsonb,
    winning_observation_id text,          -- no FK: observation is partitioned
    rule                   text not null,
    resolved_at            timestamptz not null default now(),
    primary key (customer_id, field)
);

create table decision_log (
    id            bigserial primary key,
    customer_id   uuid   not null,
    field         text   not null,
    old_value     jsonb,
    new_value     jsonb,
    rule          text   not null,
    candidate_ids text[] not null,        -- the exact set the rule ran over
    decided_at    timestamptz not null default now()
);
create index on decision_log (customer_id, decided_at desc);

create table merge_log (
    id          bigserial primary key,
    winner_id   uuid  not null,
    loser_id    uuid  not null,
    evidence    jsonb not null,           -- which keys agreed, and their strength
    actor       text  not null,           -- 'auto' or a reviewer id
    decided_at  timestamptz not null default now(),
    reversed_at timestamptz
);

create table outbox (
    id           bigserial primary key,
    customer_id  uuid  not null,
    payload      jsonb not null,
    created_at   timestamptz not null default now(),
    published_at timestamptz
);
create index on outbox (published_at) where published_at is null;

Observations are appended only when the value actually changes. Sources re-send whole records constantly and most fields are identical to last time. Before appending, compare against the latest observation for that (source, source_record_id, field); if the normalized value and tombstone flag match, drop it. This is not an optimization detail — without it the table grows with traffic instead of with change, which is roughly a twelvefold difference here.

Ingest is split from resolution because their load shapes are unrelated: ingest is spiky and must answer in single-digit milliseconds, resolution is throughput work that scales on Kafka partitions, and profile reads scale on entirely different traffic. One deployable would force all three to share a scaling decision.

Authority is configuration

The canonical field set is code — it is the schema. Which source wins a field is policy that changes without a deploy, so it is bound from configuration and validated at startup.

FieldAuthorityPolicy.java 
@Component
@ConfigurationProperties(prefix = "cdp.authority")
@Data
@Validated
public class FieldAuthorityPolicy {

    public static final int NOT_AUTHORITATIVE = Integer.MAX_VALUE;

    /** Field to its sources, best first. A source not listed may not supply that field at all. */
    private Map<CanonicalField, List<SourceSystem>> order = new EnumMap<>(CanonicalField.class);

    /** Lower is better. {@link #NOT_AUTHORITATIVE} means this source has no say here. */
    public int tier(CanonicalField field, SourceSystem source) {
        int rank = order.getOrDefault(field, List.of()).indexOf(source);
        return rank < 0 ? NOT_AUTHORITATIVE : rank;
    }

    @PostConstruct
    void requireEveryFieldToHaveAnOwner() {
        // A field with no authoritative source silently loses every value ever sent for it,
        // which looks exactly like a normalization bug from the outside. Fail at boot instead.
        EnumSet<CanonicalField> orphans = EnumSet.allOf(CanonicalField.class);
        order.forEach((field, sources) -> { if (!sources.isEmpty()) orphans.remove(field); });
        if (!orphans.isEmpty()) {
            throw new IllegalStateException("no authoritative source configured for " + orphans);
        }
    }
}

The resolver

This is the whole survivorship policy. It touches no repository, reads no current profile, and takes no clock — given the same candidates it returns the same answer on any machine, at any time, in any arrival order. That is what makes replay safe and lineage honest.

SurvivorshipResolver.java 
@Service
@RequiredArgsConstructor
public class SurvivorshipResolver {

    /**
     * Deterministic ordering within an authority tier.
     *
     * <p>The tiebreak is {@code eventId} — the source's own identifier — and NOT the observation's
     * row id. A replay from the S3 archive mints new row ids, so a row-id tiebreak would let the
     * replay settle on a different value than the original run. Convergence is the point; the
     * tiebreak has to come from the data, not from our storage.
     */
    private static final Comparator<Observation> WITHIN_TIER =
            Comparator.comparing(Observation::getSourceUpdatedAt)
                      .thenComparing(Observation::getEventId);

    private final FieldAuthorityPolicy authority;

    public Resolution resolve(CanonicalField field, List<Observation> candidates) {
        List<Observation> eligible = candidates.stream()
                .filter(o -> authority.tier(field, o.getSource()) != NOT_AUTHORITATIVE)
                .toList();

        if (eligible.isEmpty()) {
            return Resolution.empty(field, Rule.NO_AUTHORITATIVE_SOURCE, candidates);
        }

        int bestTier = eligible.stream()
                .mapToInt(o -> authority.tier(field, o.getSource()))
                .min()
                .orElseThrow();

        // Recency only ever competes inside a tier. A newer Support record must not
        // displace a Billing address, however long ago Billing last spoke.
        Observation winner = eligible.stream()
                .filter(o -> authority.tier(field, o.getSource()) == bestTier)
                .max(WITHIN_TIER)
                .orElseThrow();

        return winner.isTombstone()
                ? Resolution.cleared(field, winner, Rule.TOMBSTONE, candidates)
                : Resolution.of(field, winner, Rule.AUTHORITY_THEN_RECENCY, candidates);
    }
}

Applying a record

One transaction covers the append, the re-resolve, the audit row and the outbox row. The outbox matters here specifically: publishing after the commit means a crash between the two leaves a downstream consumer permanently disagreeing with the profile store, and nothing would ever detect it.

ResolutionService.java 
@Service
@RequiredArgsConstructor
@Slf4j
public class ResolutionService {

    private final ObservationDAO observations;
    private final ProfileFieldDAO profileFields;
    private final DecisionLogDAO decisionLog;
    private final OutboxDAO outbox;
    private final SurvivorshipResolver resolver;

    @Transactional
    public void apply(UUID customerId, List<Observation> incoming) {
        List<Observation> appended = observations.appendIfChanged(incoming);
        if (appended.isEmpty()) {
            return;                       // the source re-sent an identical record
        }

        EnumSet<CanonicalField> touched = appended.stream()
                .map(Observation::getField)
                .collect(Collectors.toCollection(() -> EnumSet.noneOf(CanonicalField.class)));

        List<FieldChange> changes = new ArrayList<>();
        for (CanonicalField field : touched) {
            Resolution next = resolver.resolve(field, observations.candidates(customerId, field));
            ProfileField current = profileFields.find(customerId, field);

            if (next.sameValueAs(current)) {
                continue;                 // resolved to what we already had: no log, no emit
            }
            profileFields.upsert(customerId, next);
            decisionLog.record(customerId, current, next);
            changes.add(FieldChange.between(current, next));
        }

        if (!changes.isEmpty()) {
            outbox.enqueue(ProfileChanged.of(customerId, changes));
        }
    }
}

Why sameValueAs and not just "we appended something". A late-arriving observation very often loses. Emitting profile.changed for it would wake every downstream consumer with an event whose before and after are identical — and at three sources re-sending full records, that is most of the traffic. The check belongs here, once, rather than in every consumer.

Build order

Each step is shippable and each one proves something the next depends on.

  1. CRM only, no identity resolution. Canonical schema, normalizer, observation append, survivorship, profile_field. Use the CRM id as the customer id. This proves the resolve-from-candidates model with none of the matching risk.
  2. Add Billing. Conflicts become real on day one. Ship the lineage endpoint with this step, not after it — the first argument about a wrong value happens here, and the endpoint is how you win it.
  3. Identity resolution on strong keys. Attach automatically; send every merge to the review queue. Watch what the queue fills with for a fortnight before automating anything.
  4. Add Support, weak keys, and automatic merges under the guardrails, using what the review queue taught you.
  5. Outbox and downstream consumers. Last deliberately: a wrong profile that nobody consumes is a bug, and a wrong profile that three systems have acted on is an incident.

Consequences worth naming

  • Append-only storage and the right to erasure are in tension. The resolution is crypto-shredding: encrypt observation values and the S3 archive with a per-customer data key, and make erasure the destruction of that key. The rows survive, unreadable, so immutability and replay hold for everyone else.
  • Changing a normalizer is retroactive. Old observations carry the old normalizerVersion and their values were normalized under the old rules. A change means a replay, and until it finishes the two versions coexist — which is why the version is on every row rather than in a config file somewhere.
  • The authority table is a business decision wearing a technical costume. It will be argued about, and the argument is healthy. Keeping it in configuration with a lineage endpoint to show its effects is what makes the argument tractable.
  • Deliberately not here: probabilistic and ML-based matching, real-time streaming segmentation, a self-serve rule builder, and cross-device identity. Each is a genuine addition; none of them is needed to produce a trustworthy record that can explain itself.
