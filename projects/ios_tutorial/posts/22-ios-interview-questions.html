These are the questions an iOS role actually asks, answered against the twenty-one lessons before this one. Short answers with the reasoning behind them, because the follow-up is always "why?" and that is the part being assessed.

Swift

Struct or class?

A struct is a value — assigning it copies. A class is a reference — assigning it shares. Default to struct, and reach for a class when you genuinely need shared identity or a lifetime other types observe.

In a SwiftUI app the reason is concrete: the framework compares values to decide what to redraw, so a model that can be mutated behind its back is a model whose changes it cannot see. Models are structs; the stores that own them are classes.

What does some View mean?

An opaque return type: "a specific type conforming to View, and I am not telling you which". The real type of a SwiftUI body is enormous and grows with every modifier. You never want to write it and the compiler wants to know it for diffing to be fast.

Not the same as any View, which erases the type and boxes it — slower, and it loses the information SwiftUI uses to compare.

When do you need [weak self]?

When a closure is stored as a property or outlives the call that created it. A closure captures strongly, so an object owning a closure that captures that object is a cycle neither side escapes.

        dismissalTasks[toast.id] = Task { [weak self] in
            try? await Task.sleep(for: self?.visibleDuration ?? .seconds(3))
            guard !Task.isCancelled else { return }
            self?.dismiss(toast.id)
        }

A closure passed to map and used immediately does not need it.

Optional handling — which form when?

?? when the fallback is obvious and local. guard let for a precondition, because it leaves the happy path unindented and the unwrapped value in scope. if let when only a branch needs it. map on an optional when you are transforming a value that may not be there. And ! essentially never in app code.

SwiftUI

What does @State actually store?

Not the value — the view struct is thrown away constantly. @State is storage SwiftUI keeps outside the view, keyed to the view's identity.

Which is why identity matters so much: change it and the state is discarded and rebuilt. That is behind both "my state reset for no reason" and "these two things are sharing state that should not be".

@State, @Binding, @Observable, @Environment — how do you choose?

Ask who owns it. This view owns it and nobody else needs it: @State. Someone else owns it and lent me write access: @Binding. Several views share it and it outlives any one of them: an @Observable class. It comes from far above and the layers in between do not care: @Environment.

The rule underneath: state lives at the lowest level that can see everything needing it.

What did @Observable change?

ObservableObject required @Published on every property and invalidated every observer when any of them changed. The macro tracks reads at the property level, so a view reading one property is not redrawn when a different one changes.

For a small type it is invisible. For a store four screens read, it is the difference between redrawing a badge and redrawing a menu.

How does SwiftUI decide to redraw?

It re-runs body, compares the resulting value tree with the previous one, and updates only what differs. Hence the rule that body must be pure and cheap — it can run when you do not expect it, more than once, and be discarded without being shown.

Practically: pass a row the data it needs rather than the whole store, and do filtering and sorting outside the body.

List versus LazyVStack?

Both are lazy. List brings swipe actions, selection, separators, the platform's insets and pull-to-refresh, and is right when your design should look like Settings. A LazyVStack starts from nothing, which is right when your rows are brand-styled cards and you would otherwise be fighting List's appearance on every one.

The trap is the one that is not lazy: a plain VStack in a ScrollView builds every child before showing the first.

Why is id: \.self risky?

Because it uses the value as identity. A collection containing two equal elements gives SwiftUI one identity for both, and rows start sharing state and animating strangely. An index-derived id is the same mistake: insert at the top and every identity shifts, so the framework believes everything changed.

Concurrency

What does @MainActor guarantee?

That the annotated code runs on the main actor, checked at compile time rather than asserted at runtime. What it does not mean is that everything runs on the main thread — an async method on a main-actor type suspends at each await, and the awaited work happens elsewhere.

How does cancellation work?

Cooperatively. Cancelling a task sets a flag; the task is expected to notice, either by checking Task.isCancelled or by calling something that throws CancellationError — Task.sleep most often.

Structured concurrency means it propagates: cancel a task and everything it awaits is cancelled too. In SwiftUI, .task gives you that for free when a view disappears.

What is actor reentrancy, and why should you care?

An actor guarantees one task executes its code at a time. It does not guarantee a method runs to completion before another starts — at every await inside an actor method, the actor can service somebody else.

So state read before an await may be stale after it. Re-check anything you depend on after awaiting. This is the check-then-act race in a new costume, and it is the one thing about actors worth being careful with.

async let or a task group?

async let when you know the operations at compile time — it is two lines and reads clearly. A task group when the number is dynamic. Both give you cancellation and error propagation; the group additionally lets you process results as they arrive.

Architecture

Is MVVM an architecture?

Only a third of one. It says a view renders and a view model holds logic, and nothing about where networking lives or what a view model may depend on. An app can be perfectly MVVM and still have a view model that builds URLs, parses JSON and caches to disk.

The decision that matters is which direction dependencies point. Repository protocols in the domain layer, implementations in the data layer, and nothing in a feature importing URLSession.

How would you make a screen testable?

Inject its dependencies rather than letting it construct them, and put anything with rules in something that does not need rendering.

protocol CatalogRepository: Sendable {
    func products() async throws -> [Product]
    func toppings() async throws -> [Topping]
    func crusts() async throws -> [Crust]
}

A test hands over a repository returning three pizzas from an array, and the view model cannot tell the difference. Follow-up you should expect: "and how do you test the network layer?" — URLProtocol, so the real session builds the real request.

Show me a pure function worth testing

    func hasSameConfiguration(as other: CartItem) -> Bool {
        guard productID == other.productID, size == other.size, crustID == other.crustID else {
            return false
        }
        return toppings.map(\.id).sorted() == other.toppings.map(\.id).sorted()
    }

Two cart lines are the same only if the product, size, crust and topping set all match. The sort is the detail worth pointing at in an interview: selection order is not part of a pizza, so {pepperoni, mushroom} and {mushroom, pepperoni} must be one configuration. Without it a customer gets two lines for the same thing; without the whole function, a plain pepperoni and one with extra cheese collapse into one and they are charged for the wrong pizza.

Why a reducer for the cart and not for everything?

Because the cart is the state four screens read, three can change, and getting it wrong charges somebody for the wrong pizza. A pure reducer makes the rules testable in microseconds, gives every mutation a name, and leaves the store holding only effects.

For four fields of screen-local form state, it would be ceremony. Knowing which is which is the actual skill, and saying so is a better answer than defending either extreme.

Singletons — what is wrong with them?

Testing, before design. A singleton is shared state every test inherits, which makes tests affect each other and "did this touch the network?" unanswerable. It also hides the dependency graph, so there is no file that tells you what the app is made of.

Practical

Where do you store an auth token, and why?

The Keychain, with kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly. AfterFirstUnlock so background work still functions with the screen locked; ThisDeviceOnly so it is never copied into an iCloud backup — a session token belongs to one device, and syncing it hands a live session to a machine the customer may not control.

Not UserDefaults, which is readable by anyone with a backup.

What happens when your app is backgrounded?

It goes inactive, then background with a short window to finish work, then suspended. From there it can be terminated with no callback at all — so anything you meant to save had to be saved before suspension.

Concretely: a debounced write must be flushed on scenePhase changing, or a customer who adds something and immediately switches apps loses it.

How do you avoid the eternal spinner?

enum ViewState<Value> {
    case idle
    case loading
    case loaded(Value)
    case empty
    case failed(message: String, isRetryable: Bool)
    // accessors and constructors follow

Make it unrepresentable. Three booleans describe eight combinations, five of them nonsense; five cases describe five real states, and the compiler insists a view handles all of them.

The questions to ask back

An interview is two-way, and these tell you more about a codebase than any answer they give about process.

  • What is your minimum deployment target, and how do you decide when to move it?
  • UIKit, SwiftUI or both — and if both, where is the boundary?
  • What does your test suite cover, and how long does it take?
  • How long from merge to a build in TestFlight?
  • What is the oldest part of the codebase, and what would you change about it?

The last one is the best question on the list. Everyone has an answer, and how specific it is tells you whether the team is allowed to look at their own code honestly.
